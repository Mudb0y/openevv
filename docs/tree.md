# What each directory is

## In the tree

`src` is the engine: hand-written C, one file per object in IBM's own module decomposition, gathered into four groups. `src/delta` is the Delta machine, which runs the language's rules. `src/klatt` is the formant synthesiser that makes the sound. `src/port` is what the port supplies itself: threads, timers, files, the landing place a backtrack jumps to, and the low arena the sixty-four bit build needs. `src/eci` is the ECI layer, which is the published interface and the machinery behind it, and it is 127 of the 163 files, so it has groups of its own. `src/eci/api` is the caller's side: both generations of the published interface, what a handle is, and the parameters and voices an instance holds. `src/eci/lang` is which languages the build has, what each is called, and what each offers -- its voice presets, its phonemes, and the romanizer that stands in front of a language written in another script. `src/eci/ssml` is the SSML reader, which text on the way in goes through before anything else. `src/eci/synth` is the synthesis thread and what it drives, `src/eci/sound` where the samples go, and `src/eci/queue` what waits in between. `src/eci/dict` is the dictionaries, the caller's and the stored kind both. `src/eci/bridge` is where ECI meets the Delta machine. `src/eci/util` is the shared small things: a hash table, a growable buffer, a fixed-block allocator, a thread, a lock, a timer. `klatt_rates.c` is the one file among the synthesiser's that is not IBM's: it builds the two resonator tables for a rate IBM never shipped, out of the formulae IBM's own four turn out to be exactly, which `make rates` holds against IBM's own arrays. The other half of the rates is in `eci_pcm.c`, which raises one from the rate the engine actually runs at rather than synthesising higher, five ways of which `EVV_UPSAMPLE` picks, a windowed sinc by default; it is the object of IBM's sound layer this port went without until then, and `eci_pcm.h` declares its arithmetic separately so `make rates` can drive it with no engine behind it.

The file names are IBM's, and they are kept that way on purpose. A file named for the object it came from can be checked against that object; renaming them would look tidier and cost real verification. The groups are not IBM's -- its libraries are a flat list of objects -- so they are ours, and an include in `src` is written as a bare name rather than a path so that a file which turns out to be in the wrong group can be moved without a line of code changing. The Makefile works the directory list out from what is on disk for the same reason.

`src/eci/dict` is nine files, seven of which are the stored dictionary's own classes, named for the objects they came from with the `win_` dropped as the rest of that layer is: `eci_key.c` is a key, `eci_translation.c` what a key means, `eci_listnode.c` one of each, `eci_skiplistnode.c` that with a tower of forward pointers on it, `eci_arraylistnode.c` the same with indices instead of pointers, which is the shape it takes in a file, and `eci_skipstore.c` the skip list itself. Only the Japanese romanizer's user dictionary uses them, so an English build links none of them; they are in `src` rather than in `rom` because they are IBM's shared layer, present in every language's object set, rather than one language's own code. `eci_dict.c` and `eci_usrdct.c` beside them are the caller's own dictionaries, which every language has.

`src/eci/ssml` is the SSML reader, twenty-three files, and it is text on the way in rather than anything the synthesiser knows about: a document becomes the annotations the engine already understands and nothing below the text filter knows the layer exists. `eci_xmltok.c` is the scanner and `eci_parserxml.c` the shell that turns its tokens into three calls; `eci_ssmlprocessor.c` is what those calls do, one handler per element; `eci_ssmlstate.c` with `eci_ssmlsayas.c` is what it remembers while it reads, over the stacks in `eci_ssmlintstack.c`, `eci_ssmlstrstack.c` and `eci_ssmllangstack.c`; `eci_ssmlmap.c` turns SSML's own values into the engine's numbers; `eci_ssmlutils.c` is the small shared things and `eci_mbconvert.c` the narrowing that lets a 256-entry scanner read UTF-8. `eci_ipatospr.c` converts a pronunciation given in IPA into the phoneme spelling an annotation uses, six languages of it. `eci_languageid.c` and `eci_langid.c` are what a document's `xml:lang` becomes, and `eci_vcinfo.c` what `<voice name>` is looked up in. `eci_filter.c`, `eci_ssmlfilter.c` and `eci_filtermanager.c` are the filter interface the whole thing hangs off, which is what `eciRegisterFilter` writes into.

`eci_xmltok_tables.c` is the one file in `src` that is lifted rather than written. The scanner is flex output, and a rule set compiled into a state machine cannot be re-derived from the machine: those eight tables are the only surviving statement of what the forty-eight rules were. `tools/engine/xmltok.py` writes the file out of IBM's object and `--check` holds the tree against it. It is IBM's data, like `lang/enus`, and `NOTICE` says so.

Five things there are not from an object. `src/delta/delta_lang.h` and `src/delta/delta_lang.c` are what lets a program have more than one language in it: a language is a table of tables rather than a set of names, and the engine reaches whichever is in force through that. `src/port/port_win32.c` is the Win32 platform layer, which the Windows build and the reference build both use and the Linux build does not. `src/port/evv_land.c` is the landing place a backtrack jumps to, which is ours because the C library's does not fit what the engine does with it. `src/delta/delta_low.c` copies the language's own data out of the program into the arena, which is what lets the program be loaded anywhere -- and therefore what lets it be a shared library. And `src/delta/delta_flags.h` is the machine's four flags and the arithmetic that sets them, which was in the interpreter and by rights belongs there; it is a header because a rule written as C makes the same comparisons and has to make them the same way, and out of line the compiler could not see that almost everything it worked out was never read.

`lang/enus` is US English. `delta_consts_enus.c` is the constant blobs the rules read, `delta_link_enus.c` the statement and field tables, `delta_sets_enus.c` the lookup sets and dictionary action tables, `delta_globals_enus.c` the variable declarations and how big a machine of this language is, `eci_ini_enus.c` the settings the engine carries -- which language it is, its voice presets and its phonemes -- and `enus.dict` the dictionary in a form a person can edit. All of it is transcribed from IBM's objects. Three more files a build compiles are not here at all: `delta_rules_enus.c` is the rules as bytecode, `delta_rules_shim_enus.c` each rule under its own name and `delta_rules_enus.h` what the rest of the module needs of both, and all three are written out of `rules` by every build rather than kept beside it. Three files are neither transcribed nor generated from the text. `delta_lang_enus.c` gathers the rest into the one table the engine knows the language by and `delta_rules_none_enus.c` is the empty list of rules-written-as-C an ordinary build links instead of the twelve megabytes, both written by `tools/module/gather.py`; and `delta_authored_enus.c` is bytes a rule of ours names by address, written by `tools/rules/consts.py` out of `rules/constants`. That last one is the only file in a module no lifter touches, which is the point of it: running a lifter again cannot lose what is in it.

Every one of those generated files has a text form beside it now, and each regenerates its own file byte for byte: `enus.globals` is the variables, `enus.settings` the settings the engine carries, `enus.statements` the statement table, `enus.sets` the lookup sets and the dictionary's actions, `enus.consts` the bytes the rules name by address, and `enus.dict` the words. `enus.globals` can also name a variable, which is how a rule written in the upper form says `set f2_in to 2000` where IBM's own names are gone. `make tables-check` is what holds the four against the tree, and `docs/language.md` says what each says and what is deliberately left out of it.

`lang/<tag>/rules` is the rules as text, and it is what a build compiles them out of. One `.dr` file to an object in the lower notation, `wrappers.up` as what each wrapper stands for, a `.up` file beside a `.dr` for a rule written in the upper form rather than lifted, `trials` naming the `.up` files the module keeps but does not build, `symbols` saying where each address a rule names falls, and `constants` for the bytes of ours. Every module in the tree has one. `docs/rules.md` says what each form is for.

Every name a module defines carries the language -- `enus_vstmtbl`, `dede_vstmtbl` -- because IBM gave them the same names in every language and a program may have several modules in it.

`lang/dede` is German, the same files under the same names with `dede` for `enus`. It is the second language lifted and the first to be built beside English: `make LANGS="lang/enus lang/dede"` puts both in one binary, and the caller chooses between them the way IBM's own interface always allowed. `docs/status.md` says how far German gets.

`lang/engb` is British English, again the same files with `engb` for `enus`. It is family one dialect one where US English is family one dialect nought, so it is the first pair of dialects of one family the language mechanism has carried.

`lang/eses` and `lang/esus` are the two Spanishes, `lang/frfr` and `lang/frca` the two Frenches, and `lang/itit` Italian, all of them the same files under the same names. That is eight of the SDK's nine; Japanese is the one not here, and `docs/status.md` says why.

`lang/plpl` is Polish, which IBM never shipped, and it is the one module that was not lifted: it was made by copying Italian's text forms and renaming them, so it is Italian until each piece of it has been replaced. `NOTICE` says what that means for the licence and `make EVVLANG=lang/plpl census` says how far it has got. What has been replaced so far is in six `.up` files under `lang/plpl/rules` -- `is_sival.up`, `is_val.up`, `it_numbr.up`, `it_phnol.up`, `it_phone.up` and `it_strss.up`, fifty-five rules between them -- with the bytes those name in `lang/plpl/rules/constants`, and `lang/plpl/plpl.codepoints` says what each of Polish's own characters arrives as, and `lang/plpl/plpl.dict` is its dictionaries as text. A build takes any set of them: `make LANGS="lang/enus lang/dede lang/engb"` puts three in one binary and a longer list puts more.

Everything in a language module is named for that module, and the build compiles whatever `.c` files a module holds. So a file that is not named for its module is either left over from an earlier lift or in the wrong place, and the build refuses it by name rather than compiling it in silently.

`rom/jajp` is the Japanese romanizer: the thing that is `jpnrom.dll` in stock Eloquence. It is code of ours rather than data of IBM's, which is why it is not in `lang/jajp`, and it is built exactly when its language is -- the Makefile compiles `rom/<tag>` beside `lang/<tag>`, so an English build carries none of it. Each file is named for the object it came from, as in `src`: `rominstance.c` is the instance the manager holds and the forwarding it does, `rominstparam.c` the parameters and errors, `unicodeconvt.c` the codeset conversion, `dictman.c` and `jpnutil.c` the accessors over the lifted tables, `dictsearch.c` the dictionary search, `userdict.c` the user dictionary a caller teaches words to, `annotation.c` the marks a caller puts in the text, `inputchar.c` the reader that turns bytes into characters, `convtinterface.c` the surface the engine speaks to, `inputmngr.c` the queue text and marks arrive on, `codeconv.c` the two codesets that are not Shift-JIS folded into the one that is, `jpath.c` the path search itself, `phrasebuf.c` where its answers become accent phrases, `numread.c` how a number becomes words, `intonphrase.c` where a speaker breathes and what pitch each phrase carries, `prosctrl.c` all of that written out as the string the synthesiser reads, `phrasetable.c` where a phrase becomes the row those two read, `kakutei.c` the one method of `TextAnalysis` that copying needs, `makereadable.c` what rewrites a date or an amount of money into words before any of it starts, `textnormalizer.c` what decides which of those a bracketed stretch of text wants, `romanizer.c` the one method of that class anything else needs, and `jprom.h` is what they share. Twelve headers beside them are maps rather than code: `txtanal.h`, `dictsearch.h`, `inputchar.h`, `romanizer.h`, `phrasebuf.h`, `jpath.h`, `numread.h`, `intonphrase.h`, `prosctrl.h`, `makereadable.h`, `textnormalizer.h` and `phrasetable.h` say where the fields of IBM's records sit, and each of them parks its pointers past the record because IBM laid them four bytes apart, and `tools/rom/offsets.py` is what keeps them true -- it checks each of the seven against the object its class is compiled into, and refuses a map with a gap or an overlap in it. The tables and dictionary they read are data and are in `lang/jajp`, lifted by `tools/rom/dictionary.py` and `tools/rom/tables.py`. `docs/japanese.md` is the account of the whole thing.

`cli` holds the two console front ends. `evv.c` is the command a person runs: options, a wave file or a pipe, and nothing printed that was not asked for. `probe.c` is the one the tests drive, which prints what the engine answered at every step. `reference/speak.c` is a third, driving IBM's engine through the published ECI names, and it is separate because those are different names for the same calls and joining them would mean a conditional around every one.

`nvda` is the NVDA add-on, which is Python rather than C because that is what a screen reader loads. `addon/synthDrivers/openevv.py` is the driver the reader talks to: the settings it shows and the turning of a speech sequence into text with annotations in it. `_openevv.py` beside it is everything below that: the library through ctypes, the one thread that is allowed to call into it, and the audio. `manifest.ini.in` is what NVDA reads to identify the add-on, with the version filled in at packing time, `build.py` does the packing, and `test` holds the three checks: `sequence.py` for the driver's half, `engine.py` for the engine layer against a library stood in for, and `windows.py`, which wants a real Windows and the real library and is where the faults have been found. Where the library has more than one language in it the driver offers each language's eight presets as voices of their own and follows a document that changes language; all three checks cover that.

`win` is the speak window and nothing else: `speak.c` with `speak.rc` and `speak.h`, the only front end that plays what the engine makes, through waveOut, and Windows-only for the same reason it exists -- that is the platform someone can be handed one file for.

`lib` is the engine under the names IBM published, so that a program expecting IBM's `eci.dll` can load ours instead. `eci_api.c` is the whole of it, one wrapper per name, and one file rather than two: the same source builds `build/eci.dll`, `build/eci32.dll` and `build/libeci.so`, differing only in what the header says a call is and in whether the platform is started from an entry point or a constructor. `eci.rc` gives both bitnesses a version resource, which is not decoration: the most used screen reader driver reads `ProductName` out of it to decide which engine it is talking to. `eci.ini` is a stub that goes beside the library because add-ons look for one and rewrite a path in it. This was in `win` until the tree was tidied, and it is out because being a DLL is how it currently ships rather than what it is: the names are the published interface, and nothing about them is Windows -- which stopped being an argument and became a build the day there was an ELF library too.

`include` is that interface as a program sees it. `eci.h` is the only file something building against this engine includes: the published names, the numbers they take, and the two macros that say how a call is made. It is not a description of the engine and holds nothing of its insides, which is the point -- `cli/evv.c`, `lib/eci_api.c` and `test/lib/dll.c` each wrote their own copy of those declarations before it existed, and three descriptions of one thing are two chances to disagree.

`docs` is one file per question rather than one per subject. Three of them are for someone building against this engine rather than on it: `using.md` is how to get from a checkout to speech in your own program, `api.md` the published interface call by call, and `quirks.md` the things that cost an afternoon if nobody says them first. The rest are for someone working on the engine. `building.md` is what you need, what to build and every variable. `rules.md` is the rules in all three forms and how a rule of ours is written and proved. `language.md` is everything else in a module and what it takes to add a language. `testing.md` is the gate, the oracle and the taps. `windows.md` is the Windows build, the library and the screen reader add-on. Those five were one file until the tree was tidied, and it had become five manuals under one name. `tree.md` is this. `status.md` is what works and what does not. `japanese.md` is the one language that does not yet, and `remaining.md` what is left of IBM's code, object by object, with what is deliberately never to be read; those two are handovers rather than descriptions, since the work they account for is not done.

`test/harness` holds the drivers the checks above run, one per question, and `reference` the same drivers built against IBM's own objects where a question needs an oracle -- `phontry.c` beside `test/harness/phonemes.c` is the newest pair of those, asking both engines what a language decided a word was made of.

`tools/engine` acts on `src`, and three of its tools are the three ways a name can be absent. `missing.py` says what our code asks for that nothing of ours answers, which a linker can answer. `census.py` says the reverse -- what IBM's objects define that nothing here has written, which the linker never can, since a function no rule calls is a function the link never asks for. And `stubs.py` says what exists and does nothing, which neither of the others can see because the symbol is there. `make missing`, `make objects` and `make stubs`.

`docs/notes` is the finished results, one to a file. These were sections of `status.md` and do not belong in a status report: an answer is worth reading for its own sake, and a report that never has anything taken out of it only grows. `polish.md` is the whole account of making a language IBM never shipped, in the order it was done. `ssml.md` is the reader and what made it checkable. `crashing-strings.md` is the one fault behind every string that kills Eloquence. `sample-rates.md` is how the engine came to speak above eleven thousand. `module-as-text.md` is what each of a module's five texts says. And `apple-eloquence.md` is the measurement against Apple's own ECI 6.1, which is a second implementation of the same interface and the only other one there is.

`test` is in three ranks, because the things in it are not of one kind. What stands at the top is what anyone runs. `matrix.sh` is the gate: every case of every language spoken and held against the recorded answers in `samples`, one file a language, with the samples and the interface's own replies hashed separately. `suite.sh` is the oracle beside it, running the categories of cases through both engines, with `compare.sh` doing one category, and `cases` is the text itself. A case file named for a language is that language's -- `plain-dede.txt` beside `plain.txt` -- and `EVV_LANG` is what picks between them and between the two binaries to match; the `-plpl` ones are ours rather than IBM's, since there is no Polish original and nothing to compare against. `hash.sh` and `samples.sha256` are the two-second smoke test, one English sentence, and one of the two checks that need neither Wine nor IBM; `crashers.sh` and `cases/crashers.txt` are the other, and hold the engine to answering at all on text the original dies on.

`test/harness` is the second rank: twenty-one files for the things the suite cannot see at all, which is why each needs a harness of its own rather than a case. `instances.c`, `interrupt.c`, `landing.c`, `rate.c`, `rates.c`, `inikeys.c`, `voices.c`, `pieces.c` and `stopthread.c` are an instance thrown away and made again, an utterance interrupted, a backtrack landed on from a thread that never planted it, the sample rate changed on an instance that speaks into the caller's buffer, that same rate set to one IBM never shipped and the tables built for it held against IBM's own, the settings reader asked for a key that is not there, the eight voices the caller may edit on an instance just made, one text spoken whole and then in the pieces the add-on would cut it into, and an utterance stopped from a thread that is not the one speaking. `stopthread.c` is the only one built for Windows as well, because Wine is where the thing it tests used to fail. Five more are a different arrangement again: the file is compiled twice, once against our engine and once against IBM's objects, and a script runs both and diffs what they print, because a call no rule makes cannot be reached by speaking a sentence. `prims.c` with `prims.sh` is the machine's own primitives one at a time; `romprims.c` with `romprims.sh` the romanizer's converters, which no sentence reaches either; and `ipa.c` with `ipa.sh`, `xmltok.c` with `xmltok.sh` and `ssml.c` with `ssml.sh` the SSML layer -- the IPA converters over every code point, the XML scanner over 46 documents, and the whole reader over 176. The last of those is the sharpest oracle in the tree, because what it compares is text rather than samples, so a difference names itself. Unlike the first nine, all five want Wine and the SDK.

`romcan.c` and `romcan.sh` are in that rank too, and are for a language written in another script. A romanizer stands between the text and the engine, and until it is transcribed no word of such a language reaches the engine at all -- so `reference/romtap.c` records every call IBM's romanizer manager makes and every answer it gets, and `romcan.c` replays those answers as a romanizer with no language in it. The samples then have to be IBM's, which says the whole engine below that seam is right, and the conversation has to be IBM's too, which says our manager asks the same questions. `EVV_ROMCAN_PARAMS=real` hands the parameter half to the romanizer's own code instead of the recording, which is what proves that half.

`test/lib` is the third rank: three that go through the library the way another program would rather than linking the engine. `dll.c` and `dll.py` speak through it once from C and once through ctypes, and text beginning with a `<' goes through the SSML reader first -- which is a third question again, since turning the reader on means handing the library's own entry point back to it across the boundary. `langs.py` is for a library with more than one language in it: it speaks all of them from one process and checks that none of them moved.

`tools` is grouped by what a tool acts on rather than by which direction it goes, because most of them go both ways. `tools/evv.py` is the only file not in a group: it says where the tree is and how one tool loads another, so that neither is written down in every file.

`tools/rules` is the whole rules toolchain, in both directions. `lift.py` reads the compiled rules out of IBM's objects and `emit.py` writes them out as the bytecode the interpreter runs. `lower.py` is the notation one operation to a line, read and written, and it is the machine's rather than any language's. `notation.py` is the front door: it lifts IBM's objects into that form, holds the tree against them, and writes the files a build compiles. `upper.py` compiles a rule written as what it does into the same form, and `consts.py` lays down the bytes such a rule names by address. `decompile.py` turns the bytecode into C, with `patterns.py` beside it, which is the classifier four other tools import: it says which shapes the rules are made of, and therefore how big a decompiler has to be. `shape.py`, `wrappers.py` and `arms.py` answer the three other questions anyone asks of the rules -- how much of the control flow is a shape C has a word for, what each wrapper rule stands for, and what each arm of a dictionary rule lays down. `check-c.sh` holds the rules written as C against the same rules left as bytecode, and `check-upper.sh` holds a rule written in the upper form against the one IBM compiled, by speaking both and setting every call against the other. `EVV_LANG_DIR` points the decompiler and the classifier at a language other than English.

`tools/module` is everything in a language module except the rules. `link.py` is the statement and field tables, `sets.py` the lookup sets and the dictionary's action tables, `globals.py` the variable declarations and the size of the machine they decide, `settings.py` the settings blob with the two constants beside it that say which language a module is, and `gather.py` the one table the engine knows a language by. Those first four go both ways, which is the point of them: each writes its piece of a language as text and reads it back, and each has one writer for the C so that a lift and a text cannot come out differently. `dump` writes the text, `regenerate` holds the C written from it against the tree, and `write` puts it there. `dict.py` and `lexicon.py` are the dictionaries, as a file a person can edit and as the words the engine actually reads. `alphabet.py`, `codepoints.py` and `phonemes.py` are a language's own characters and sounds -- what letters it has and what each is, what byte each arrives as, and every phoneme's name, numbers and rule beside each other. `census.py` says how much of one module is still the module it was copied from, which is what `make census` runs. Each takes the language as an argument and answers `enus` when not given one.

`tools/engine` acts on the engine in `src` rather than on a language in `lang`. `runtime-tables.py` is the Delta runtime's numeric tables and `klatt-tables.py` the synthesiser's, both copied across rather than recomputed, because their last-place rounding is part of the sound. `xmltok.py` writes the XML scanner's eight tables, which are the only lifted data in `src`. `disassemble.py` breaks a COFF object into per-function disassembly, which is what made the synthesiser readable in the first place: MSVC gave every function its own section starting at address zero, so one dump of the whole object says nothing. `tools/engine/missing.py` says what the build still asks the original for, and has to keep answering zero. `crashers.py` grows a set of strings the engine cannot survive out of a few that are known, by trying every one-letter change to each and keeping whatever kills it too; it is what `test/cases/crashers.txt` was made with.

`tools/rom` is the Japanese romanizer. `dictionary.py` and `tables.py` take its static dictionary and the three objects that are mostly table. `offsets.py` is of a different kind from every other tool: it holds a map of one of IBM's records against the object the class was compiled into. `TextAnalysis` is 946,216 bytes and every class in the Japanese analyser reads its fields directly, so `rom/jajp/txtanal.h` had to be worked out before any of them could be written; this takes every offset IBM's own code uses on one and refuses any that falls outside a named region, then checks that the regions tile the object exactly. It takes the name of a class -- `textanalysis` or `dictsearch` -- and knows which objects hold that class's own code, since one class may be spread over several: `DictSearch` is spread over seven, which is worth checking against `nm` rather than assuming, because a list that is short makes the checker narrower than it claims to be. `docs/japanese.md` says what that established.

`tools/sdk` unpacks IBM's SDK: `extract.sh` for the objects the port was read out of and `extract-langs.sh` for the eight other languages. Neither is needed to build, since what they write is not in the tree and what the build compiles is.

`tools/measure` is the three tools that turn a question about the sound into a number rather than an opinion. `pitch.py` measures what a voice does with pitch and rhythm -- ours or a recording of a person, in the same units, which is what makes intonation something other than a matter of taste. `rates.py` reads the same sentence spoken at several sample rates and says where the formant peaks are and how much energy sits above what eleven thousand can carry. `say.sh` speaks some text with the engine as the dictionary currently has it, so that a change to a word can be heard rather than read about, and it plays as an ordinary client of the sound server and touches nothing else.

`.github` holds the workflow that builds both binaries on every push and cuts a release with the Windows exes when a tag is pushed.


## Not in the tree

`analysis` holds the objects extracted from IBM's SDK by `tools/sdk/extract.sh`, and the eight other languages lifted by `tools/sdk/extract-langs.sh`. It is the input to every lifter and none of it is needed to build. The reference material the port was read with -- IBM's headers for four API generations, symbol maps for 199 objects, the phoneme alphabet, the SDK's sample code and the original source tree listing -- was in the tree as `research` until 20 August 2026 and is in git history at that commit.

`lang/jajp` is not in the tree either, and is lifted by the commands in `docs/japanese.md`. A language module that cannot make an instance would fail any build that named it, and Japanese cannot until its romanizer is finished. Most of it is the romanizer's own data: nine megabytes of C for the dictionary and a further two hundred thousand bytes of tables, all of it IBM's and all of it lifted in two commands.

`build` is output: `evv` and `probe` with their objects under `obj`, the thirty-two bit pair with theirs under `obj32`, and `reference/speak.exe` with its own. Each of those object directories has one directory per set of languages inside it, because a build of one and a build of another give their objects the same names and a stale one is newer than the source that should replace it. The archives and the test binaries carry the languages for the same reason -- `probe-dede` and `probe-enus-dede` beside `probe` -- so that switching back does not link the English probe against whatever was built last. `build/delta_langs_*.c` is written by the Makefile and says which languages a build has in it. Two things under `lang` are output too, which is why neither is tracked. `delta_rules_<tag>.c`, `delta_rules_<tag>.h` and `delta_rules_shim_<tag>.c` are the rules as the engine runs them, written out of `lang/<tag>/rules` by every build, two seconds a language -- the text is the source and a second copy of it in the tree could only ever be the stale one. And `delta_rules_c[0-9][0-9]_<tag>.c` is those rules decompiled into C, thirty-two files rather than one because thirteen megabytes in a single translation unit is seven minutes of compiler that no number of cores can shorten. `.wine` is a Wine prefix for the reference binary, and is not wanted on Windows.
