# What each directory is

## In the tree

`src` is the engine: hand-written C, one file per object in IBM's own module decomposition. `eci_` files are the ECI layer, which is the published interface and the machinery behind it. `delta_` files are the Delta machine, which runs the language's rules. `klatt_` files are the formant synthesiser that makes the sound. `port_` and `evv_` files are what the port supplies itself: threads, timers, files, and the low arena the sixty-four bit build needs. `klatt_rates.c` is the one file among the synthesiser's that is not IBM's: it builds the two resonator tables for a rate IBM never shipped, out of the formulae IBM's own four turn out to be exactly, which `make rates` holds against IBM's own arrays. The other half of the rates is in `eci_pcm.c`, which raises one from the rate the engine actually runs at rather than synthesising higher, five ways of which `EVV_UPSAMPLE` picks, a windowed sinc by default; it is the object of IBM's sound layer this port went without until then, and `eci_pcm.h` declares its arithmetic separately so `make rates` can drive it with no engine behind it.

The names are IBM's, and they are kept that way on purpose. A file named for the object it came from can be checked against that object; renaming them would look tidier and cost real verification.

Six files are the stored dictionary's own classes, and they are named for the objects they came from with the `win_` dropped as the rest of that layer is: `eci_key.c` is a key, `eci_translation.c` what a key means, `eci_listnode.c` one of each, `eci_skiplistnode.c` that with a tower of forward pointers on it, `eci_arraylistnode.c` the same with indices instead of pointers, which is the shape it takes in a file, and `eci_skipstore.c` the skip list itself. Only the Japanese romanizer's user dictionary uses them, so an English build links none of them; they are in `src` rather than in `rom` because they are IBM's shared layer, present in every language's object set, rather than one language's own code.

Five things there are not from an object. `src/delta_lang.h` and `src/delta_lang.c` are what lets a program have more than one language in it: a language is a table of tables rather than a set of names, and the engine reaches whichever is in force through that. `src/port_win32.c` is the Win32 platform layer, which the Windows build and the reference build both use and the Linux build does not. `src/evv_land.c` is the landing place a backtrack jumps to, which is ours because the C library's does not fit what the engine does with it. `src/delta_low.c` copies the language's own data out of the program into the arena, which is what lets the program be loaded anywhere -- and therefore what lets it be a shared library. And `src/delta_flags.h` is the machine's four flags and the arithmetic that sets them, which was in the interpreter and by rights belongs there; it is a header because a rule written as C makes the same comparisons and has to make them the same way, and out of line the compiler could not see that almost everything it worked out was never read.

`lang/enus` is US English. `delta_consts_enus.c` is the constant blobs the rules read, `delta_link_enus.c` the statement and field tables, `delta_sets_enus.c` the lookup sets and dictionary action tables, `delta_globals_enus.c` the variable declarations and how big a machine of this language is, `eci_ini_enus.c` the settings the engine carries -- which language it is, its voice presets and its phonemes -- and `enus.dict` the dictionary in a form a person can edit. All of it is transcribed from IBM's objects. Three more files a build compiles are not here at all: `delta_rules_enus.c` is the rules as bytecode, `delta_rules_shim_enus.c` each rule under its own name and `delta_rules_enus.h` what the rest of the module needs of both, and all three are written out of `rules` by every build rather than kept beside it. Three files are neither transcribed nor generated from the text. `delta_lang_enus.c` gathers the rest into the one table the engine knows the language by and `delta_rules_none_enus.c` is the empty list of rules-written-as-C an ordinary build links instead of the twelve megabytes, both written by `tools/gen-lang.py`; and `delta_authored_enus.c` is bytes a rule of ours names by address, written by `tools/delta-consts.py` out of `rules/constants`. That last one is the only file in a module no lifter touches, which is the point of it: running a lifter again cannot lose what is in it.

Every one of those generated files has a text form beside it now, and each regenerates its own file byte for byte: `enus.globals` is the variables, `enus.settings` the settings the engine carries, `enus.statements` the statement table, `enus.sets` the lookup sets and the dictionary's actions, `enus.consts` the bytes the rules name by address, and `enus.dict` the words. `enus.globals` can also name a variable, which is how a rule written in the upper form says `set f2_in to 2000` where IBM's own names are gone. `make tables-check` is what holds the four against the tree, and `docs/building.md` says what each says and what is deliberately left out of it.

`lang/<tag>/rules` is the rules as text, and it is what a build compiles them out of. One `.dr` file to an object in the lower notation, `wrappers.up` as what each wrapper stands for, a `.up` file beside a `.dr` for a rule written in the upper form rather than lifted, `trials` naming the `.up` files the module keeps but does not build, `symbols` saying where each address a rule names falls, and `constants` for the bytes of ours. Every module in the tree has one. `docs/building.md` says what each form is for.

Every name a module defines carries the language -- `enus_vstmtbl`, `dede_vstmtbl` -- because IBM gave them the same names in every language and a program may have several modules in it.

`lang/dede` is German, the same files under the same names with `dede` for `enus`. It is the second language lifted and the first to be built beside English: `make LANGS="lang/enus lang/dede"` puts both in one binary, and the caller chooses between them the way IBM's own interface always allowed. `docs/status.md` says how far German gets.

`lang/engb` is British English, again the same files with `engb` for `enus`. It is family one dialect one where US English is family one dialect nought, so it is the first pair of dialects of one family the language mechanism has carried.

`lang/eses` and `lang/esus` are the two Spanishes, `lang/frfr` and `lang/frca` the two Frenches, and `lang/itit` Italian, all of them the same files under the same names. That is eight of the SDK's nine; Japanese is the one not here, and `docs/status.md` says why.

`lang/plpl` is Polish, which IBM never shipped, and it is the one module that was not lifted: it was made by copying Italian's text forms and renaming them, so it is Italian until each piece of it has been replaced. `NOTICE` says what that means for the licence and `make EVVLANG=lang/plpl census` says how far it has got. What has been replaced so far is in six `.up` files under `lang/plpl/rules` -- `is_sival.up`, `is_val.up`, `it_numbr.up`, `it_phnol.up`, `it_phone.up` and `it_strss.up`, fifty-five rules between them -- with the bytes those name in `lang/plpl/rules/constants`, and `lang/plpl/plpl.codepoints` says what each of Polish's own characters arrives as, and `lang/plpl/plpl.dict` is its dictionaries as text. A build takes any set of them: `make LANGS="lang/enus lang/dede lang/engb"` puts three in one binary and a longer list puts more.

Everything in a language module is named for that module, and the build compiles whatever `.c` files a module holds. So a file that is not named for its module is either left over from an earlier lift or in the wrong place, and the build refuses it by name rather than compiling it in silently.

`rom/jajp` is the Japanese romanizer: the thing that is `jpnrom.dll` in stock Eloquence. It is code of ours rather than data of IBM's, which is why it is not in `lang/jajp`, and it is built exactly when its language is -- the Makefile compiles `rom/<tag>` beside `lang/<tag>`, so an English build carries none of it. Each file is named for the object it came from, as in `src`: `rominstance.c` is the instance the manager holds and the forwarding it does, `rominstparam.c` the parameters and errors, `unicodeconvt.c` the codeset conversion, `dictman.c` and `jpnutil.c` the accessors over the lifted tables, `dictsearch.c` the dictionary search, `userdict.c` the user dictionary a caller teaches words to, `annotation.c` the marks a caller puts in the text, `inputchar.c` the reader that turns bytes into characters, `convtinterface.c` the surface the engine speaks to, `inputmngr.c` the queue text and marks arrive on, `codeconv.c` the two codesets that are not Shift-JIS folded into the one that is, `phrasebuf.c` where the path search's answers become accent phrases, `romanizer.c` the one method of that class anything else needs, and `jprom.h` is what they share. Four headers beside them are maps rather than code: `txtanal.h`, `dictsearch.h`, `inputchar.h`, `romanizer.h`, `phrasebuf.h` and `jpath.h` say where the fields of IBM's records sit, and each of the four parks its pointers past the record because IBM laid them four bytes apart, and `tools/rom-offsets.py` is what keeps them true -- it checks each of the five against the object its class is compiled into, and refuses a map with a gap or an overlap in it. The tables and dictionary they read are data and are in `lang/jajp`, lifted by `tools/lift-rom.py` and `tools/lift-romtables.py`. `docs/japanese.md` is the account of the whole thing.

`cli` holds the two console front ends. `evv.c` is the command a person runs: options, a wave file or a pipe, and nothing printed that was not asked for. `probe.c` is the one the tests drive, which prints what the engine answered at every step. `reference/speak.c` is a third, driving IBM's engine through the published ECI names, and it is separate because those are different names for the same calls and joining them would mean a conditional around every one.

`nvda` is the NVDA add-on, which is Python rather than C because that is what a screen reader loads. `addon/synthDrivers/openevv.py` is the driver the reader talks to: the settings it shows and the turning of a speech sequence into text with annotations in it. `_openevv.py` beside it is everything below that: the library through ctypes, the one thread that is allowed to call into it, and the audio. `manifest.ini.in` is what NVDA reads to identify the add-on, with the version filled in at packing time, `build.py` does the packing, and `test` holds the three checks: `sequence.py` for the driver's half, `engine.py` for the engine layer against a library stood in for, and `windows.py`, which wants a real Windows and the real library and is where the faults have been found. Where the library has more than one language in it the driver offers each language's eight presets as voices of their own and follows a document that changes language; all three checks cover that.

`win` is the Windows front, and it holds two different things. `speak.c` with `speak.rc` is the speak window: the only front end that plays what the engine makes, through waveOut, and Windows-only for the same reason it exists -- that is the platform someone can be handed one file for. `eci_api.c` is the library: the engine exported under the names IBM published, so that a program expecting IBM's `eci.dll` can load ours instead. `eci.ini` is a stub that goes beside the library because add-ons look for one and rewrite a path in it.

`docs` holds this file, `building.md` for every target and variable, `status.md` for what works and what does not, `japanese.md` for the one language that does not yet, and `remaining.md` for what is left of IBM's code, object by object, with what is deliberately never to be read. The last two are handovers rather than descriptions, since the work they account for is not done.

`test` holds `suite.sh`, which runs the categories of cases through both engines, `compare.sh`, which does one category, and `cases`, the text itself. A case file named for a language is that language's -- `plain-dede.txt` beside `plain.txt` -- and `EVV_LANG` is what picks between them and between the two binaries to match. `hash.sh` and `samples.sha256` are one of the two checks that need neither Wine nor IBM; `crashers.sh` and `cases/crashers.txt` are the other, and hold the engine to answering at all on text the original dies on. `dll.c` and `dll.py` speak through the library the way something else would, once from C and once through ctypes. `langs.py` is for a library with more than one language in it: it speaks all of them from one process and checks that none of them moved. `instances.c`, `interrupt.c`, `landing.c`, `rate.c`, `rates.c`, `inikeys.c`, `voices.c`, `pieces.c` and `stopthread.c` are harnesses for the things the suite never does: an instance thrown away and made again, an utterance interrupted, a backtrack landed on from a thread that never planted it, the sample rate changed on an instance that speaks into the caller's buffer, that same rate set to one IBM never shipped and the tables built for it held against IBM's own, the settings reader asked for a key that is not there, the eight voices the caller may edit on an instance just made, one text spoken whole and then in the pieces the add-on would cut it into, and an utterance stopped from a thread that is not the one speaking. `stopthread.c` is the only one of them built for Windows as well, because Wine is where the thing it tests used to fail. `prims.c` is a harness of a different kind: it calls the machine's own primitives one at a time and is compiled twice, once against our engine and once against IBM's objects, because a call no rule makes cannot be reached by speaking a sentence. `prims.sh` runs both and diffs them, and unlike the others it wants Wine and the SDK. `romprims.c` and `romprims.sh` are the same arrangement for the romanizer's converters, which no sentence reaches either.

`romcan.c` and `romcan.sh` are for a language written in another script. A romanizer stands between the text and the engine, and until it is transcribed no word of such a language reaches the engine at all -- so `reference/romtap.c` records every call IBM's romanizer manager makes and every answer it gets, and `romcan.c` replays those answers as a romanizer with no language in it. The samples then have to be IBM's, which says the whole engine below that seam is right, and the conversation has to be IBM's too, which says our manager asks the same questions. `EVV_ROMCAN_PARAMS=real` hands the parameter half to the romanizer's own code instead of the recording, which is what proves that half.

`tools` holds four kinds of thing. The lifters turn IBM's objects into the C in `lang`: `extract.sh` and `extract-langs.sh` unpack the SDK, `lift-rom.py` and `lift-romtables.py` take the Japanese romanizer's dictionary and its tables, `delta-lift.py` reads the compiled rules, `delta-emit.py` writes them out as bytecode, `delta-link.py` and `delta-sets.py` the tables beside them, `gen-globals.py` the variable declarations and the size of the machine they decide, `lift-ini.py` the settings blob together with the two constants beside it that say which language a module is, `gen-lang.py` the table that gathers one language into the one thing the engine knows it by, and `delta-tables.py`, `gen-tables.py` and `catalogue.py` the synthesiser's own tables. Each of them takes the language as an argument and answers `enus` when not given one. The decompiler is `delta-decompile.py` with `delta-census.py`, which turn that bytecode into readable C; `EVV_LANG_DIR` points those two at a language other than English.

The compiler is the other direction, from text to what the engine runs. `delta-lower.py` is the notation one operation to a line, read and written, and it is the machine's rather than any language's; `delta-notation.py` lifts IBM's objects into that form, holds the tree against them and writes the two files a build compiles; `delta-upper.py` compiles a rule written as what it does into the same form; `delta-consts.py` lays down bytes a rule of ours names. `upper-check.sh` is what says an authored rule is the rule it stands in for, by speaking both and holding every call against the other.

`crash-search.py` belongs to none of those groups: it grows a set of strings the engine cannot survive out of a few that are known, by trying every one-letter change to each and keeping whatever kills it too. It is what `test/cases/crashers.txt` was made with.

The four lifters beside the rules go both ways as well, which is why they are in both lists: `gen-globals.py`, `lift-ini.py`, `delta-link.py` and `delta-sets.py` each write their piece of a language as text and read it back, and each has one writer for the C so that a lift and a text cannot come out differently. `dump` writes the text, `regenerate` holds the C written from it against the tree, and `write` puts it there.

`rom-offsets.py` is of a fourth kind: it holds a map of a record against the object it was read out of. `TextAnalysis` is 946,216 bytes and every class in the Japanese analyser reads its fields directly, so `rom/jajp/txtanal.h` had to be worked out before any of them could be written; this takes every offset IBM's own code uses on one and refuses any that falls outside a named region, then checks that the regions tile the object exactly. It takes the name of a class -- `textanalysis` or `dictsearch` -- and knows which objects hold that class's own code, since one class may be spread over several: `DictSearch` is spread over seven, which is worth checking against `nm` rather than assuming, because a list that is short makes the checker narrower than it claims to be. `docs/japanese.md` says what that established.

The analysers answer questions about what is in there: `delta-lexicon.py`, `delta-dict.py`, `delta-wrappers.py`, `delta-arms.py`, `delta-shape.py`, `missing.py`, `lang-census.py`, which says how much of one module is still the module it was copied from, `lang-alphabet.py`, which reads and writes a language's alphabet and what each of its characters is, `lang-codepoints.py`, which says what each of its own characters arrives as, and `lang-phonemes.py`, which puts every phoneme's name, numbers and rule beside each other, `pitch.py`, which measures what a voice does with pitch and rhythm -- ours or a recording of a person, in the same units, which is what makes intonation something other than a matter of opinion, and `rate-compare.py`, which reads the same sentence spoken at several sample rates and says where the formant peaks are and how much energy sits above what eleven thousand can carry, since whether a new rate is worth having is otherwise a matter of opinion too. `say.sh`, `delta-check.sh` and `upper-check.sh` are the checks that need no Wine.

`reference` builds IBM's own binary from IBM's own objects: under Wine on Linux, and on Windows as it stands. It is all that is left of the differential harness that made the port. `speak.c` drives it through the published names, and two files stand wrappers in front of IBM's own functions so that where two engines stop agreeing can be read off rather than guessed at. `tap.c` takes four functions inside the engine, and `make -C reference tap` builds it. `romtap.c` takes the eight public methods of the romanizer manager, which is the seam a language written in another script goes through, and `make -C reference TAG=jajp romtap` builds that; what it writes is what `test/romcan.c` replays. The head of each says why it can only be those functions. `jptry.c` is the driver that settled what IBM's Japanese does with Japanese script, and `jajp_shim.c` supplies the two names Japanese's own object set does not carry.

`.github` holds the workflow that builds both binaries on every push and cuts a release with the Windows exes when a tag is pushed.

`docs` is this.

## Not in the tree

`analysis` holds the objects extracted from IBM's SDK by `tools/extract.sh`, and the eight other languages lifted by `tools/extract-langs.sh`. It is the input to every lifter and none of it is needed to build. The reference material the port was read with -- IBM's headers for four API generations, symbol maps for 199 objects, the phoneme alphabet, the SDK's sample code and the original source tree listing -- was in the tree as `research` until 20 August 2026 and is in git history at that commit.

`lang/jajp` is not in the tree either, and is lifted by the commands in `docs/japanese.md`. A language module that cannot make an instance would fail any build that named it, and Japanese cannot until its romanizer is finished. Most of it is the romanizer's own data: nine megabytes of C for the dictionary and a further two hundred thousand bytes of tables, all of it IBM's and all of it lifted in two commands.

`build` is output: `evv` and `probe` with their objects under `obj`, the thirty-two bit pair with theirs under `obj32`, and `reference/speak.exe` with its own. Each of those object directories has one directory per set of languages inside it, because a build of one and a build of another give their objects the same names and a stale one is newer than the source that should replace it. The archives and the test binaries carry the languages for the same reason -- `probe-dede` and `probe-enus-dede` beside `probe` -- so that switching back does not link the English probe against whatever was built last. `build/delta_langs_*.c` is written by the Makefile and says which languages a build has in it. Two things under `lang` are output too, which is why neither is tracked. `delta_rules_<tag>.c`, `delta_rules_<tag>.h` and `delta_rules_shim_<tag>.c` are the rules as the engine runs them, written out of `lang/<tag>/rules` by every build, two seconds a language -- the text is the source and a second copy of it in the tree could only ever be the stale one. And `delta_rules_c[0-9][0-9]_<tag>.c` is those rules decompiled into C, thirty-two files rather than one because thirteen megabytes in a single translation unit is seven minutes of compiler that no number of cores can shorten. `.wine` is a Wine prefix for the reference binary, and is not wanted on Windows.
